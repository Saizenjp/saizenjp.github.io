# 생태계 점검 — 연결성·QR·재고↔정산·외부 시스템·전환 리스크 (2026-10-30)

Min 지시(2026-10-30): 「재고관리도 나중에 정산에서 다 같이 볼 수 있어야 하는 거 아니야? · 여러 가지로 이 생태계를 한번 점검 · QR 코드로 손님이 활용할 수 있는 부분은 최대한 · 연결성과 효율성 극대화 · 실제 사용 중인 시스템들을 모두 정리하고 이걸로 바꾸려면 리스크가 없어야 함」

이 문서는 **구조·연결·빈 곳·리스크**만 적는다. 경영 수치(매출·원가·급여 등)는 §3-2 규칙에 따라 넣지 않는다.
2026-08 의 `docs/ops-flow-review.md`(손님 동선 검수)를 이어받아, 그 뒤 두 달의 변화를 반영한다.

## 1. 지금의 생태계 지도

### 1-1. 입력(소스) → 저장 → 화면
```
엠클릭(메리트투어 예약 시스템) ──xlsx 2종(예약리스트·일행별예약)──▶ step1 ─┬▶ bookings·passengers·guests·guest_members  (야마나미 권역 4숙소)
                                                                        └▶ partner_bookings·partner_members           (자회사 상품, SQL 159 — 적용 대기)
member_codes(회원 평생 레지스트리)  ◀─ groupcodes(코드 미보유 회원 배정)
room_inventory·room_closures ◀─ room/shizu(객실 마스터·폐쇄)
menu_items ◀─ menu(품목·세율) · cart_types/cart_units ◀─ cart(카트 등록) · golf_courses ◀─ course
```
- **읽는 화면(36)**: 랜딩 1 + hub 35. 모두 같은 Supabase 를 publishable key + RLS 로 읽는다. 로그인 없이 보는 것은 안내 모니터(RPC 15개 anon)와 손님 QR 페이지(bill.html)만.
- **쓰는 화면**: step1(등록) · room/shizu(방) · course/cart(골프) · pos/kitchen(주문) · settle/settle_report(정산·마감) · frontdesk(체크인·메모·워크인·출발 안내) · dinner(장소·제외·공개) · board(공지·홍보·문구) · housekeeping(청소 완료) · inventory(입출고) · outings(행사·신청) · transfer(배차·승차) · admin/groupcodes(권한·코드).
- **검산**: `data_audit()` 22종(정합성 + 통계 검산 — 모니터·보고서·세율) → audit.html [재검수]. 변경 이력 `change_log`(불변) + `audit_log`(행 단위, 자동배정 잡음 제외).

## 5. 재고 ↔ 정산 — 「정산에서 다 같이 본다」로 가는 길
**현재**: `inv_items`(현재고·단가·거래처)·`inv_txns`(입고/사용/실사 원장, 입고에만 금액)·`v_inv_spend`(월 사입 집계) 는 재고 화면에만 있다. POS 가 팔아도 재고는 줄지 않고(수동 사용 처리), 정산 보고서에는 사입·재고 금액이 없다. 메뉴 품목(`menu_items`)과 재고 품목(`inv_items`)은 **연결 컬럼이 없다**.

| 단계 | 할 일 | 효과 | 리스크 |
|---|---|---|---|
| 1 | **메뉴 ↔ 재고 품목 매핑(간단 레시피)** — `menu_recipes(menu_id, item_id, qty)`; 메뉴 관리에 「이 메뉴 1개 = 생맥주 350ml 1 …」 입력 | 어떤 메뉴가 어떤 재고를 쓰는지 정의 | 입력 부담(음료부터, 요리는 주재료만) |
| 2 | **POS 전송 → 재고 자동 사용**(트리거: kitchen_tickets/charges 생성 시 inv_txns `사용` 기록, 취소 시 되돌림) | 재고가 실시간. 실사 차이 = 로스 | 매핑 없는 메뉴는 그대로(수동) |
| 3 | **정산 보고서 월보에 「사입·재고」 블록**(월 사입 금액(거래처별)·기말 재고 금액·매출 대비 비율) + `data_audit` 검산 짝 | 원가율이 보인다(Min 보류 항목 「사입 관리」의 결론) | 수치는 화면·DB 에만, 저장소에 안 남긴다 |

권한: 재고 금액은 돈이라 **settle 영역 읽기**로 둔다(지금 inv_* 읽기는 로그인 전체 — 단가가 보이므로 재검토 대상).

## 7. 실제 사용 중인 시스템 정리(전환 전 목록)
### 7-1. 저장소·DB 에서 확인되는 것

| GitHub Pages | 화면 호스팅(public) | main 자동 배포 | 공개 저장소 — PII·수치 금지 원칙(§3-2) |

## 8. 전환 리스크 없이 가는 원칙(체크리스트)
1. **병행 기간**: 새 화면으로 바꾸는 업무는 2주 이상 **옛 방식과 둘 다** 하고 숫자를 맞춘다(마감·식수·방배정).
2. **되돌리기 수단이 먼저**: Supabase Pro 일일 백업 · `booking_snapshots` · `change_log`(불변) · 자동배정 되돌리기 · 시즈 자동배정 undo — 새 기능도 undo/스냅샷을 먼저 둔다.
3. **검산 짝**: 숫자를 만드는 기능은 `data_audit()` 에 짝을 넣어 [재검수] 가 계속 본다(§3-3).
4. **오프라인 폴백**: 인터넷 단절 시 빨간 띠·장바구니 보존·종이 기록 → 복구 후 입력(hardware-list 운영 규칙).
5. **권한**: 새 카드는 자기 권한 키(area_tree) — 자회사 계정처럼 보는 범위를 좁힐 때는 RLS 까지 확인(지금 일반 표는 로그인 전체 읽기).
6. **설명서**: 화면마다 SO_HELP(ko/ja/en) 가 운영 절차다 — 담당자가 바뀌어도 화면에서 읽는다. **매일 누르는 순서**(아침: 체크인 확인·코스 공개·석식 공개 / 저녁: 일 마감)를 한 장으로 묶는 것이 다음 문서 후보.
7. **공개 저장소 규칙**: PII·경영 수치·비밀키 금지(§3-2) — 전환 중 받은 원본 파일은 세션 임시 폴더에서만.
